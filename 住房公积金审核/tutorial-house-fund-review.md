## 场景与目标

上海市住房公积金提取审核是一个真实的政务业务场景：居民提交提取申请（购房、租房、装修、大病医疗等）与一堆证明材料（身份证、房产证、合同、发票等 PDF 扫描件），审核员要判断**这次提取是否合规**。

常见咨询/预审场景：

- "我在临港买了新房，能提公积金吗？需要什么材料？"
- "我想提取公积金交房租，一年最多能提多少？"
- "申请人提交了购房合同和不动产权证，材料齐全吗？"
- "这份申请有没有异常风险（频繁购房、价格异常等）？"

**核心挑战**：这不是单一能力的问题，而是**多种能力的组合**——
- 要懂法规（提取条件、材料清单、额度频次）→ 需要 Agentic RAG
- 要会读 PDF（识别证件信息、交叉核验）→ 需要 PDF OCR Skill
- 要识别业务异常（红线清单）→ 需要防御性设计
- 要输出规范结论（给审核员看的 checklist）→ 需要严格输出契约
- 要守住边界（遇到法规没写的情况不乱编）→ 需要明确的"不知道"出口

**目标**：用三层分离架构（System Prompt + Skill + references）把这四件事装进一个 Agent，让它既能聊天咨询，也能做材料预审，输出格式化的审核结论。

## 总体架构一览

```
nexau.json                  ← 入口：声明 Agent 和排除文件，用于发布到 North Agent Cloud
agent.yaml                  ← 骨架：模型配置、工具注册
  ├── systemprompt.md        ← 大脑：角色定位 + 处理流程 + 输出规范
  ├── tools/                 ← 手脚：8 个标准化工具（文件读写、搜索、Shell…）
  ├── skills/
  │   ├── house-fund-review/ ← 领域知识：审核工作流 + 法规原文
  │   │   ├── SKILL.md
  │   │   └── references/    ← 三份法规原文 .md
  │   └── pdf_to_md/         ← 能力扩展：PDF OCR 转文本
  │       ├── SKILL.md
  │       └── scripts/
```

其中 `nexau.json` 是项目的清单文件，用于将 Agent 发布到 North Agent Cloud：

```json
{
  "agents": {
    "house_fund_review": "agent.yaml"   // 声明项目中包含哪些 Agent 及其配置文件
  },
  "excluded": [".nexau/", ".env", "__pycache__/"]  // 发布时排除的文件（密钥、缓存等）
}
```

- `agents` — 键是 Agent 名称，值是对应的配置文件路径。一个项目可以包含多个 Agent。
- `excluded` — 发布时需要排除的目录和文件，避免将 `.env`（含 API Key）等敏感内容上传。

这个结构的核心理念是：**每一层只做一件事，层与层之间通过文件路径松耦合**。

## 设计要点 1：三层分离架构

大多数人写 Agent 会把所有内容塞进一个巨大的 System Prompt。这个项目把内容分成了三层：

| 层级 | 文件 | 职责 | 变更频率 |
|------|------|------|---------|
| 指挥层 | `systemprompt.md` | 角色定义、处理流程、输出规范 | 低 |
| 知识层 | `skills/house-fund-review/SKILL.md` | 业务规则、审核逻辑、风险清单 | 中 |
| 原文层 | `skills/.../references/*.md` | 法规条文原文 | 几乎不变 |

**为什么这样做？**

```
❌ 反面教材：所有内容塞进 System Prompt
   → 改一个条款要翻 3000 行 prompt
   → 法规更新要重新测试整个 Agent
   → token 浪费严重（每次对话都加载全部法规）

✅ 本项目的做法：按需加载
   → System Prompt 只有 60 行，告诉 Agent "怎么干活"
   → Skill 200 行，告诉 Agent "业务规则是什么"
   → 法规原文只在需要时才 read_file 读取
```

**关键收益**：法规更新时，只需要替换 `references/` 下的文件，不需要改动 Agent 的任何逻辑代码。

## 设计要点 2：System Prompt 只当"指挥官"

看这个 System Prompt 的第一句话：

```
你是上海市住房公积金提取申请的智能审核助手。
```

一句话定义角色。接下来的内容，不是在教 Agent 公积金知识，而是在给它一个**行动手册**：

```markdown
# 处理流程
1. 加载 Skill — 读取技能文件，明确审核步骤
2. 查阅法规 — 按需读取法规原文
3. 解析附件 — PDF 转文本
4. 交叉比对 — 多份材料信息一致性核验
5. 输出结论 — 按格式输出
```

这 5 步就是 Agent 的"决策主循环"。注意它的巧妙之处：

- **先加载知识，再开始干活** — 确保 Agent 不会在没有看规则的情况下回答问题
- **查阅法规是"按需"的** — 不是一次性读完所有法规，而是根据 Skill 的指引去找对应条款
- **解析附件排在比对之前** — 先拿到数据，再做判断，符合人类审核员的思维方式

**设计原则**：System Prompt 回答的是"你是谁"和"你怎么干活"，不回答"你知道什么"。知识放在 Skill 里，原文放在 references 里。

## 设计要点 3：Skill 是可插拔的"领域大脑"

`SKILL.md` 的设计是这个项目最精彩的部分。先看它的元数据：

```yaml
---
name: house-fund-review
description: |
  上海市住房公积金提取申请审核助手。根据《住房公积金管理条例》...
  当用户提到住房公积金提取、公积金审核、公积金咨询...时，使用此 skill。
  即使用户只是随口问一下公积金能不能提、怎么提、需要什么材料，也应触发此 skill。
---
```

注意 `description` 中的最后一句："即使用户只是随口问一下……也应触发"。这句话的作用是**降低触发门槛**，避免 Agent 在模糊场景下不知道该不该用这个 Skill。

Skill 内部的结构也值得细看，它分成了 6 个步骤，每个步骤都是**可独立执行**的：

```
第一步：识别提取类型      ← 分类问题
第二步：判断提取条件      ← 规则匹配
第三步：核验所需材料      ← 清单比对
第四步：说明频次和额度    ← 数据查询
第五步：风险识别          ← 异常检测
第六步：家庭成员和代办    ← 补充规则
```

**为什么分步骤很重要？**

LLM 在处理复杂任务时容易"跳步"或"漏项"。把审核流程拆成明确的 6 步，相当于给 Agent 一个 checklist：即使某一步骤的结果很简单，Agent 也不会跳过。

## 设计要点 4：让 Agent 自己查法规，而不是背法规

这是一个非常关键的架构决策。两种方案对比：

```
方案 A：把法规全文塞进 System Prompt
  → 优点：Agent 立刻就能引用
  → 缺点：三份法规 ~500 行，占用大量 context
  → 缺点：法规更新需要改 prompt
  → 缺点：Agent 可能"记混"不同条款

方案 B（本项目）：法规存文件，Agent 按需查阅
  → 优点：System Prompt 精简，留更多空间给用户输入
  → 优点：Agent 查到的是原文，不是"记忆中的大意"
  → 优点：法规更新只需替换文件
  → 代价：多一次 read_file 调用（可接受）
```

本项目选择了方案 B，并通过 Skill 中的**法规索引**来指导 Agent 该查哪个文件的哪一条：

```markdown
核心法规依据

1. 住房公积金管理条例.md — 全国性基础规定（提取范围见第24条）
2. 上海市住房公积金管理若干规定.md — 上海市地方法规（提取情形见第7条）
3. 上海市住房公积金提取管理办法.md — 最具体的操作指南（日常审核最常用）
```

这段话同时教了 Agent 三件事：
1. **文件在哪** — 直接给出了文件名
2. **优先级是什么** — "大多数场景以《提取管理办法》为主要依据，遇到该办法未覆盖的情形再向上查找"
3. **入口在哪** — "提取范围见第24条"直接给了条款号

这种 **"索引 + 原文分离"** 的模式，让 Agent 既知道去哪找答案，又能引用原文，而不是靠训练数据里的"印象"来回答。

## 设计要点 5：用表格代替散文

SKILL.md 中大量使用了表格来组织信息。对比两种写法：

```
❌ 散文写法：
购买自住住房时需要提供购房合同、不动产权证和购房发票。如果是外地购房，
还需要提供户籍或缴存地凭证。建造翻建大修的需要提供原不动产权证或土地证、
审批文件和付款凭证……

✅ 表格写法（本项目）：
| 提取类型 | 对应条款 | 核心材料 |
|---------|---------|---------|
| 购买住房 | 第十三条 | 购房合同、不动产权证、购房发票 |
| 建造/翻建/大修 | 第十四条 | 原不动产权证/土地证、审批文件、付款凭证 |
```

表格的好处：
1. **LLM 更容易精准定位** — 模型做表格查找比从段落中提取信息更准确
2. **减少遗漏** — 每一行都是独立条目，不会因为段落太长而"看丢了"
3. **便于维护** — 改一行不影响其他行

类似地，提取类型识别也用了表格 + 关键词映射：

```markdown
| 编号 | 提取情形 | 关键词 |
|------|---------|--------|
| (一) | 购买自住住房 | 买房、购房、新房、二手房、共有产权房 |
| (四) | 租赁住房 | 租房、房租、公租房、市场租赁、保障性租赁 |
```

"关键词"列是专门给 LLM 看的：当用户说"我想提公积金交房租"，LLM 可以直接匹配"房租"→ 第（四）项租赁住房。这比让 LLM 自己"理解"用户意图要可靠得多。

## 设计要点 6：边界情况的防御性设计

一个 Agent 的质量差距，往往不在常规场景，而在**边界情况的处理**。这个项目在两个地方做了精心设计：

### 6.1 风险识别清单

```markdown
### 第五步：风险识别和严格审核提示

1. 异常频次购房提取 — 在外省市县级城市以购房名义提取频次明显异常
2. 价格异常 — 购房总价与账户余额接近，且房屋单价明显偏离当地市场
3. 频繁交易 — 所购房屋一年内多次交易
4. 婚姻关系异常 — 同一人多次变更婚姻关系购房
```

这些不是法规里的原话，而是从实务经验中提炼出来的**审核红线**。把它们明确写出来，Agent 在审核时就会主动检查，而不是等用户问"有什么风险"。

### 6.2 "不知道就说不知道"

```markdown
- 不编造法规条款。遇到法规未覆盖的边界情况，明确告知
  "建议咨询上海市公积金管理中心（12329）"
```

这是最重要的一条。LLM 最危险的行为是"自信地编造"。这句话给了 Agent 一个**合法的退出路径**：遇到不确定的情况，承认不知道并给出求助渠道（12329 热线），比编一个答案要安全得多。

### 6.3 容易遗漏的规则显式提醒

```markdown
- 不要遗漏"配偶可同时提取"和"加装电梯可提取父母子女公积金"
  等家庭成员联动提取规则
```

这类提醒的价值在于：它不是教 Agent 新知识（Skill 里已经有了），而是**强调容易被忽略的关键点**。就像给审核员的便签纸，写着"别忘了检查配偶"。

## 设计要点 7：PDF 处理的工程化封装

这个项目需要处理用户提交的证件扫描件。PDF 处理的设计有三个值得学习的点：

> ⚠️ **pdf_to_md 当前仅支持互联网版本**。政务外网版本正在开发中，后续将由平台统一提供 PDF 解析能力——上传的 PDF 经平台解析后，文本内容将**自动存入沙盒**，开发者无需自行准备 OCR 相关 Skill 和 API Key。

### 7.1 Skill + 脚本分离

```
skills/pdf_to_md/
  ├── SKILL.md              ← 告诉 Agent "什么时候用、返回什么"
  └── scripts/pdf_to_md.py  ← 实际的 OCR 处理逻辑
```

SKILL.md 面向 Agent，用自然语言描述输入输出；Python 脚本面向机器，处理实际的 API 调用和并发。

注意脚本通过环境变量 `OCR_API_KEY` 获取 OCR 服务的 API Key。

### 7.2 System Prompt 中的核验指引

PDF 转完文本只是第一步，System Prompt 还告诉 Agent 转完之后该看什么：

```markdown
## 解析后的核验要点
- 证件持有人姓名与申请人是否一致
- 房产证上的地址是否在允许提取的地域范围内
- 合同/协议的签署日期是否在有效期内
- 金额信息是否与申请提取金额匹配
- 多份材料之间的信息是否相互印证
```

这段话把"看 PDF"变成了"审核 PDF"。没有这段指引，Agent 可能只是把 PDF 内容读出来然后总结，有了这段指引，Agent 会**主动做交叉验证**。

## 设计要点 8：输出格式即质量控制

Skill 中定义了两种输出格式模板：

**咨询类输出**：
```
## 审核结论     ← 结论先行，不要让用户翻到最后才知道结果
## 依据         ← 必须引用条款编号
## 所需材料     ← 材料清单
## 提取频次与额度
## 注意事项     ← 没有则省略
```

**材料预审输出**：
```
✅ 已提供且符合要求的材料
❌ 缺少的必要材料
⚠️ 需要进一步确认的材料
```

这不仅是格式要求，更是**质量控制机制**：

1. **"结论在前，依据在后"** — 强制 Agent 先给结论再解释，避免长篇大论却不给答案
2. **"引用法规必须标注条款编号"** — 可验证性，用户可以自己去查原文核实
3. **"✅❌⚠️ 三级标记"** — 结构化的状态表达，比"基本没问题但有些地方要注意"清晰百倍

## 动手实践：构建你自己的专业 Agent

根据以上分析，总结出构建专业 Agent 的 8 条核心原则：

### 原则清单

| # | 原则 | 一句话 |
|---|------|-------|
| 1 | 三层分离 | System Prompt 管流程，Skill 管知识，References 管原文 |
| 2 | Prompt 只做指挥官 | 告诉 Agent "怎么干活"，不告诉它"你知道什么" |
| 3 | Skill 可插拔 | 用元数据 description + 低触发门槛设计，让 Agent 知道何时启用 |
| 4 | 知识按需加载 | 原文存文件 + 索引指引，不塞进 prompt |
| 5 | 表格优于散文 | 分类、材料、条件、额度等信息用表格呈现 |
| 6 | 显式处理边界 | 风险清单、"不知道就说不知道"、容易遗漏的提醒 |
| 7 | 工具结果要引导 | 不只是"用工具"，还要告诉 Agent 拿到结果后做什么 |
| 8 | 输出格式 = 质量控制 | 定义输出模板，强制结论先行、引用条款、状态标记 |

### 快速模板

如果你要做一个类似的专业审核/咨询 Agent，可以按这个模板来：

```
agent/
  ├── agent.yaml               # 复制本项目的，改模型配置即可
  ├── systemprompt.md           # 按以下结构写
  │
  │   一句话角色定义
  │   # Skill 加载（指向你的 skill）
  │   # 处理流程（3-6 个步骤）
  │   # 工具使用说明（如果有特殊工具）
  │   # 输出规范
  │   # 关键注意事项（边界情况、防幻觉）
  │
  ├── tools/                    # 标准工具集，通常直接复用
  └── skills/
      └── your-domain/
          ├── SKILL.md          # 按以下结构写
          │
          │   --- (元数据：name + description，描述触发条件)
          │   # 核心知识来源（索引 + 优先级）
          │   # 工作流程（分步骤，每步用表格）
          │   # 输出格式模板
          │   # 重要原则
          │
          └── references/       # 原始知识文档
              ├── 法规1.md
              └── 法规2.md
```

### 写 Skill 的 5 个检查项

写完 SKILL.md 后，用这 5 个问题自查：

- [ ] **触发条件够宽吗？** — description 中是否覆盖了用户可能的各种说法？
- [ ] **步骤够细吗？** — 每一步是否只做一件事？是否有"太大"的步骤需要拆分？
- [ ] **表格够多吗？** — 分类、条件、材料等信息是否都用表格了？
- [ ] **退出路径有吗？** — 遇到不确定的情况，Agent 是否知道该说"不知道"并给出求助渠道？
- [ ] **容易遗漏的规则标出来了吗？** — 有没有在"注意事项"里显式提醒那些容易被跳过的规则？

---

> 好的 Agent 不是 prompt 写得多，而是结构设计得好。把知识、流程、格式分清楚，让 LLM 在正确的框架下发挥能力——这才是 Agent 工程的核心。
